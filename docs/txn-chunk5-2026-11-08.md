# Chunk 5: one modifying operation, as a transaction

2026-11-08, branch `debian-base`. Goal from `CUA-AgentOS_goal.md`: start with one reversible system operation, add a
durable journal, recovery after interruption, postcondition checks and rollback; then interrupt it on purpose.

## Baseline before the change (2026-11-08)
From a clean rebuild: Alpine gates 01–08 all exit 0 (rubric 100/100), and the amd64 Debian image rebuilt with the
chunk 4 broker passes `tests/test-debian-img.sh` 22/22. The broker broke nothing.

## The operation, and why this one
`config.set_ntp`: write `/etc/systemd/timesyncd.conf.d/50-agentd-ntp.conf`, restart `systemd-timesyncd`, and confirm it.

- It is useful on the hardware we target: the Pi 5 has no battery clock, so the time server decides whether TLS works
  at all on the first boot (`CLOCK_WAIT` exists for exactly that).
- It is reversible with bytes alone: one file, and deleting it returns the system to the distribution default.
- It can be checked independently of the write (below), which a lot of config changes cannot.
- It cannot lock the person out or take the network down, so it needs no approval prompt; a restart of
  `NetworkManager` still does.

The server is **not** free text. Like the unit table, the list is compiled in: `time.cloudflare.com`,
`time.google.com`, `pool.ntp.org`, `in.pool.ntp.org`. The request carries one of those strings or it is rejected, and
what gets written is the broker's own `&'static str`, never a byte from the request.

## The check is the daemon's answer, not the file
After the restart the broker asks `timedatectl show-timesync --property=SystemNTPServers`, which is
`systemd-timesyncd` reporting the configuration it actually loaded over D-Bus. If that list does not contain the
server, the change is rolled back. Writing the file proves nothing: the daemon may not have read it, may have failed
to start, or may be reading a different drop-in.

It is a "contains" check, not an equality check, because systemd *appends* list settings such as `NTP=` across
drop-ins instead of replacing them. The reported outcome says exactly that, and prints the whole list.

## The transaction
`agentd/src/txn.rs` (moved out of `agentd/src/main.rs`, where it had been serving capability installs since cycle 06,
and now shared by both binaries, unchanged):

- `put`: temp file in the same directory, `O_EXCL`, `fsync`, `rename`, `fsync` of the directory.
- `staged_put`: before touching the target, copy its prior bytes and mode into the transaction directory, then write
  `journal.json` (`[[path, had_prior], ...]`), then write the target. Every step is durable before the next one.
- `rollback`: newest change first, restoring bytes and mode, or deleting a file that did not exist before.
- `end_txn`: remove the transaction directory, then `fsync` its parent. This is the commit point.
- `recover`: roll back whatever a journal describes, drop leftover `.agentd-tmp` files, and close the transaction.

The broker's transaction directory is `/var/lib/agentd-broker/txn` (`StateDirectory=agentd-broker`, 0700 root).
`ProtectSystem=strict` still applies: `ReadWritePaths=` grants exactly `/etc/systemd/timesyncd.conf.d`, which
`postinst` creates.

## Recovery runs in three places
1. **At boot:** `agentd-broker-recover.service`, a oneshot ordered `Before=systemd-timesyncd.service` (and before both
   agentd sockets), so an interrupted change is undone *before* the daemon reads the file and before any new work can
   ask for one. The broker is socket-activated, so without this unit nothing would run at boot.
2. **At socket activation:** the broker recovers before it answers its first request, so a crash is repaired without
   waiting for a reboot.
3. **Before every `config.set_ntp`:** recovery is idempotent and cheap, and a transient failure (no disk space) is
   then retried rather than remembered. If recovery cannot finish, the request is refused and nothing is touched.

## What the person is told
On success: `systemd-timesyncd now lists <server> as a time server (it confirms it, "<list>")`.
On a rollback: `could not set the time server to <server>: <why>. The previous setting is back.`
If the rollback itself fails, the message says so instead of claiming the old state is back. The audit log
(`/var/log/agentd-broker/audit.jsonl`) gains the phases `rolled_back` (with `clean`), `recovered` (with the paths and
`restored`) and `recovery_failed`.

## Proof: `tests/test-txn-recovery.sh`
A throwaway KVM guest on a qcow2 overlay of the Debian 13 cloud image (the base image is never written, but the
guest's own disk survives a reboot, which `-snapshot` does not allow). `CUTS` power cuts, default 2. 14 checks:

| Check | What it proves |
|---|---|
| `set_ntp_verified` | the plain path: file written, daemon confirms, no journal left |
| `set_ntp_again` | repeating it changes nothing and still verifies |
| `set_ntp_rejects` | 7 values off the list (including `"pool.ntp.org\nNTP=..."`, a list, null, a number, the wrong unit) change nothing |
| `set_ntp_rollback` | a real post-write failure (the unit cannot restart) restores the prior bytes **and** mode 644, audits `rolled_back`, and says so |
| `recover_no_journal` | a transaction directory with no journal yet: nothing outside it was touched |
| `recover_before_write` | journalled, target not yet replaced |
| `recover_after_write` | target replaced with a different mode, plus a half-written `.agentd-tmp`: all undone |
| `recover_new_file_removed` | a file that did not exist before is deleted again |
| `recover_after_kill` | 8 × SIGKILL at a random point (0–400 ms) inside a real change: always fully old or fully new |
| `set_ntp_no_space` | no room for the write-ahead backup: the change never starts |
| `recover_at_boot` | a crash left before the commit is undone at the next boot, and `systemd-timesyncd` starts with the old setting |
| `recover_unit_ok` | the boot unit itself exits 0 |
| `consistent_after_power_cut` | after QEMU is killed mid-change: consistent file, no journal, daemon running |
| `set_ntp_after_power_cut` | and the operation still works afterwards |

**There are no crash points in the binary.** The stages are crafted on disk exactly as an interrupted transaction
leaves them, and the interruptions are real: `SIGKILL` on the broker, and `kill -9` on QEMU from the host while
changes run back to back. Nothing reachable in a shipped build can be asked to crash.

Run: `scripts/build-deb.sh && tests/test-txn-recovery.sh` (about 6 min for two cuts; no API key, no network service).

## Limits, honestly
- **shortcut:** `set_ntp_no_space` mounts a tiny tmpfs over the state directory instead of filling the guest's root
  filesystem. It reproduces `ENOSPC` where the journal is written, which is the case that matters, but not a root
  filesystem that is full for everything else.
- One modifying operation, and no operation that *clears* the drop-in again; a rollback only undoes the last change.
- The broker's rate limit (3 changes per unit per 10 minutes) is counted in memory and resets if the broker restarts.
  The test uses that on purpose to clear the count between cases.
- The power cut is a `kill -9` of QEMU. It drops everything the guest had not written, which is the same loss a real
  power pull causes, but it does not exercise the SD card's own write cache. **The Pi 5 power pull is still to do**,
  by the owner: `tests/test-txn-recovery.sh` is the amd64 half of the evidence only.
- Checked in an emulator (KVM, amd64). The arm64 image has not been rebuilt since the broker landed.
