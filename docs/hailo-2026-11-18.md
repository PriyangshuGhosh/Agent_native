# Local model tier on the AI HAT+ 2 (goal 6), 2026-11-18

Hardware: the user's Raspberry Pi 5 (8 GB) + Raspberry Pi AI HAT+ 2 (Hailo-10H, its own 8 GB). The OS stays on the
Pi; the model runs on the HAT. All results below came from the real board over the debug link (`build/debug/pi.log`).

## Setup (now `scripts/setup-hailo.sh`, run as root on the Pi)
- The HAT is detected with no config change (PCIe `1e60:45c4`). `dtparam=pciex1_gen=3` was added to `config.txt`
  (and to `scripts/build-debian-img.sh`).
- Driver and runtime come from the Raspberry Pi archive that the image already uses: `h10-hailort` and
  `h10-hailort-pcie-driver` 5.1.1 (plus `linux-headers-$(uname -r)` and build-essential, about 15 min on the Pi).
  Its DKMS install failed and it fell back to a plain build: **after a kernel update, rerun the script**.
  Firmware loads in 2.6 s; `hailortcli fw-control identify` reports HAILO10H, firmware 5.1.1.
- `hailo-ollama` comes from Hailo's GenAI Model Zoo 5.1.1 (public URL, sha256 pinned in the script; it is not in
  the apt archive). As shipped it listens on `0.0.0.0:8000` and the models folder is mode 777. The script switches it
  to `127.0.0.1` and gives the folder to a dedicated `hailo-ollama` system user, which also runs the server under a
  hardened unit.
- Models offered: qwen2.5-instruct 1.5B, qwen2 1.5B, qwen2.5-coder 1.5B, deepseek-r1-distill-qwen 1.5B,
  llama3.2 3B. Pulled: `qwen2.5-instruct:1.5b` (2.2 GB on the SD card).
- Pi RAM use stayed at about 320 MB with the model loaded; the server process itself is about 14 MB RSS.

## What the model can and cannot do (measured)
- API: Ollama-style `/api/chat`; `"format": "json"` is ignored; `num_predict` is honoured (an answer that rambled for
  21 s took 4.5 s with a 24-token cap).
- It cannot write our JSON plans (0/2 valid). It follows instructions better in the user message than in the system
  message (4/12 lines in the format against 1/12). Arithmetic is unreliable (17×23 came out as 591, then 401).
- Its worst answer was a plausible but wrong choice: "set the ntp server to time.google.com" became
  `SERVICE status networkmanager`, which is read-only but would have reported success.

## Design that follows (agentd/src/route.rs)
The local model only classifies the request into one line: `CHAT: …`, `READ <time|kernel|disk|uptime|memory>`,
`SERVICE status <cron|timesyncd|networkmanager>`, or `ESCALATE`. agentd builds the plan itself. Two deterministic
checks surround it: a request that contains a change verb (set, restart, install, …) never reaches the local model,
and a READ/SERVICE choice must name something the request mentions. Anything else goes to Gemini. Repairs never go
to the local tier.

## Results through agentd on the Pi (after the checks)
| Request | Route | Time |
|---|---|---|
| hi there | local CHAT | 2.4 s |
| what kernel am I on | local READ kernel, verified | 1.4 s |
| is cron running | deterministic (no model) | 0.2 s (broker) |
| set the ntp server to time.google.com | straight to Gemini (change verb) | Gemini only |
| how long has this machine been up / is the wifi service working / which ntp server am I using / how much ram is in use | local answer refused or handed up, then Gemini | +1.6-2.3 s |

So with this model, the HAT answers greetings and some reads in about 1.5-2.5 s, and adds about 2 s to requests it
cannot handle. Every outcome was correct, and nothing wrong ran. The `set_ntp` test changed the real setting; it was
put back afterwards (no override, the image default).

## Model comparison (same prompt, 30 labelled requests: 22 the local tier should handle, 8 it should hand up)
Benchmark: the local prompt from `route.rs`, run on the HAT with the server restarted and warmed up before each model.
Logs: `build/evidence-2026-11-18/hailo-bench/` (`run2.log`, `live-qwen2.log`). "Wrong" counts answers that survive agentd's
checks (lenient parsing of `READ time.` / `status:`, the choice must fit the request, a service question is never a read).

| Model | Handled locally | Wrong | Median | First load |
|---|---|---|---|---|
| **qwen2:1.5b** (now the default) | **14/22** | 0 (4 before the checks) | 1.3 s | 60 s |
| qwen2.5-coder:1.5b | 10/22 | 0 | 1.3 s | 87 s |
| qwen2.5-instruct:1.5b | 10/22 | 0 (1 before the checks) | 2.4 s | 12 s |
| deepseek_r1_distill_qwen:1.5b | unusable: it writes `<think>` reasoning first, so no answer within the cap; 8-23 s | | | |
| llama3.2:3b | not tried: about 3.2B parameters (over the goal's < 3B), and the SD card had 4 GB left | | | |

All 8 requests that must be handed up were handed up by every model. Live through agentd on the Pi with qwen2:1.5b:
8 requests, all ended correct; its three earlier misfires were caught by the checks and went to Gemini.
- `hailo-ollama` 5.1.1 **aborted (SIGABRT) while switching models** (`replacing model`, about 2 min, then the crash;
  systemd restarted it). agentd uses one model, so this does not happen in normal use; switch models with a restart.
- Disk: the unused models were removed afterwards (their blobs in `/usr/share/hailo-ollama/models/blob`; manifests kept, so
  `/api/pull` can fetch them again; the server's `/api/delete` returns HTTP 500). Root went from 81% to 32% used.

## Open
